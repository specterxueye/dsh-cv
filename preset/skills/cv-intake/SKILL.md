# 拷问式建档与项目取舍（CV Intake）

> **机制出处**：frontier 轮次提问法改造自 [mattpocock/skills](https://github.com/mattpocock/skills) 的 `grilling` 技能（MIT License, Copyright (c) 2026 Matt Pocock）。本文是**重写**，不是逐字复制：上游的公理是"事实归你查、决策归用户"，建档恰好相反，差异见 §3。
> **路径约定**：仓库根 = `$env:DSH_CV_ROOT`；个性数据写 `users\<用户名>\`。
> **用户问「怎么装 / 怎么用」时**：先读 `docs\安装与使用.md` 再回答（安装三步、自检命令、触发词表、升级/卸载、常见问题表），**不要凭记忆描述安装步骤**。

## 1. 它解决什么

新用户建档的真实成本**不是不愿意说，是不知道该说什么**：面对"请介绍你的实习经历"，多数人回一句"就是做后端开发"就没了，于是事实基线空洞、简历只能写空话。

本引擎把建档从"挤牙膏式 3 问 / 轮"改成**批量 frontier + 每题带推荐答案**：用户看到的是选项和一个默认答案，回复成本从"写一段话"降到"1✅ 2改成 X"。

**它只管采集与裁决，不管写作**：写作规则仍归 `resume-writing` 与 `data\rules\`；本技能产出的是**事实基线与项目可见性清单**，之后照 `preset\prompts\02-workflow.md` 继续走。

## 2. 核心机制：frontier 轮次

**frontier = 前置条件都已落定、现在就能问的问题集合**。一轮把整个 frontier 问完，**每题给推荐答案**，然后停下来等答复，再重算 frontier 进入下一轮。

> 依赖本轮其他未决问题的问题，属于**下一轮**，不要塞进本轮。

单轮格式：

```
❓ **Q1** - **<问题标题>**：<问题正文，可含多个选项>

➡️ <推荐答案；素材不足时写"待你补一句"而不是编>

---

❓ **Q2** - **<问题标题>**：<问题正文>

➡️ <推荐答案>
```

每轮开头一行进度提示：`本轮 6 问（第 2/7 轮）· 每题都可回"跳过/没有"`。

## 3. 两类问题必须分流（与上游的最大差异）

| 类型 | 判定 | 处理 |
|---|---|---|
| **只有用户知道的事实** | 学历、实习产出、项目真实边界、政治面貌、意向城市 | **必须问用户**，且给推荐答案／选项降低回答成本 |
| **机器可自查的事实** | 成绩单、证书原件、个人项目仓库 README／代码量／依赖、实习单位材料 | **派 subagent 去查**（`subagent` 工具），不占用户；查到的写进事实基线 `source`，查不到的降级为"问用户" |
| **决策** | 选哪几个项目、口径怎么定、写不写某段 | 问用户，**用户不点头不得实施** |

上游写"事实归你查、决策归用户"——在建档里只对第二类成立。**把第一类当"该自己查"会去翻一个空文件系统，把第一类当决策题会逼用户在不是选择的地方做选择。**

## 4. 两个场景，两种档位

| 场景 | 档位 | 节奏 | 产出 |
|---|---|---|---|
| **A 建档**（`resume-writing` 阶段 1） | **温和档** | 每轮 ≤7 问、每题带默认答案、允许"跳过/没有"、按 `references\frontier-建档问题树.md` 的 7 轮推进 | `<名字>-事实基线.json` + `<名字>-画像.md` |
| **B 项目取舍**（`resume-writing` 阶段 3，JD 理解之后） | **尖锐档** | 一轮列完全部候选项目的取舍，逐项给建议与理由，允许反驳 | `projectVisibility` 清单 → 并进 `changerequest-*.json` |

**温和档不是放水**：可以跳过的是"现在答不出"，不是"含糊过去"。用户说"大概 20 万行吧"这种**估数**，如实记 `status: "pending"` 并注明"用户估数、无材料佐证"，**不得**当成确认事实写进简历。

## 5. 场景 A：建档（温和档）

按 `references\frontier-建档问题树.md` 分轮推进，顺序：基本信息 → 教育 → 实习/工作 → 项目 → 校园 → 技能奖项 → 定位与口径。

纪律：

1. **一轮问完整个 frontier**，不要问一题等一题；用户可一次答完或只答部分。
2. **每题都有推荐答案或选项**；没有依据就把选项列全（如"角色：主导／负责模块／参与"），不要写"请详细描述"。
3. **可自查项先派 subagent**（§3 第二类）；能在后台查的，不占用用户注意力，也别为它卡住整轮。
4. **禁止代答**：不得替用户填写任何未确认的事实；不得"合理推测"实习规模、项目级别、数字。
5. **待确认纪律**：无材料佐证的写 `status: "pending"`；`pending` 事实不得写入简历（`data\rules\00-总则.md`）。
6. **收口**：frontier 清空且用户明确确认后，才写 `<名字>-事实基线.json` 与 `<名字>-画像.md`；写盘后回 `resume-writing` 阶段 2。
7. **轮数上限**：用户要求限轮数时以用户为准；默认 7 轮内收口，超出的问题降级为"建档后补"清单，不硬拖。

## 6. 场景 B：按 JD 裁决项目可见性（尖锐档）

**触发**：`jd-<公司>-<岗位>.json` 已产出之后、写《改动申请单》之前。

**流程**：

1. 取候选池：`users\<用户名>\项目素材库.md` ＋ 蓝本内已有但 `visible: false` 的项目。
2. 按 `references\jd-project-fit.md` 的六个维度逐项打分，产出**建议点亮 3-4 项**＋建议收起项（说明"为什么它这次不占版面"）。
3. **一轮 frontier 全列**：每个候选项目一行——命中的 JD 要求 / 建议 show 或 hide / 理由 / 页数影响 / 用户可反驳的点。
4. 用户裁决后，把结果写进改动申请单的 `projectVisibility` 与 `changes`（`op: "visibility"`），**仍要走阶段 3.5 确认门**：本轮裁决是输入，不是批准。
5. 硬边界：
   - **未显示 ≠ 删除**：收起的项目留在 JSON 里（`visible: false`），随时切回。
   - **用户明确排除项永不显示**（如社会实践、预科经历）。
   - **不许为了命中关键词凑项目**：命中不了就写进缺口清单，如实说明。
   - 建议数量按一页约束（≤4 项）；项目级别与角色不得为了贴合 JD 拔高。

## 7. 反模式（一律不许）

- ❌ 一次只问一个问题，让用户等下一轮才知道还有什么要问。
- ❌ 问题不带推荐答案 / 选项（等于把"不知道说什么"的负担还回用户）。
- ❌ 派 subagent 去"查"只有用户知道的事，或反过来拿"用户你得自己去翻文件"顶掉可自查项。
- ❌ 用拷问结果直接生成简历——**确认门在阶段 3.5，不在本技能**。
- ❌ 用户说"跳过"就自己编一个默认事实填进基线。
