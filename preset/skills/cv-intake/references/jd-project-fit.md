# 按 JD 取舍项目（场景 B · 尖锐档）

> 何时用：`jd-<公司>-<岗位>.json` 已产出之后、写《改动申请单》之前。
> 一句话原则：**这一步是"选择"，不是"美化"**——只决定点亮哪几项、每项往哪个角度讲；不许为了命中关键词拔高级别、加角色、编数字。

## 一、六维打分（每维 0-2 分，满分 12）

| 维 | 0 分 | 1 分 | 2 分 | 判据来源 |
|---|---|---|---|---|
| **D1 关键词命中** | 一条不中 | 中软性/加分项 | 中硬性要求或核心技术栈 | `jd-*.json` 的 `hardRequirements` / `keywords` |
| **D2 职能同型度** | 不同职能 | 同大类（如都属后端） | 同职能同场景（如都是 Agent 编排） | JD 岗位描述 |
| **D3 级别与真实性** | 说不清级别 | 课程设计/实验/大作业 | 真实项目/中标/竞赛获奖 | 事实基线 `projects[].level` |
| **D4 角色主导度** | 参与 | 负责模块 | 独立完成/主导 | `projects[].role` |
| **D5 可量化与可溯源** | 无任何指标 | 有指标但出处弱 | 指标可从材料复现（过 `audit-facts.mjs`） | 事实溯源清单 |
| **D6 差异化** | 与已选项目高度重复 | 部分重叠 | 补上别人没有的能力面 | 候选池横向比较 |

**建议区间**：`≥8` 点亮并**核心置顶**；`5-7` 备选（看一页余量）；`≤4` 建议收起。**始终点亮 3-4 项**（一页约束）。

## 二、呈现格式（一轮问完，可反驳）

先给一张总表，再逐项给理由：

```
❓ **Q1** - **这 3 项点亮、1 项收起，同意吗？**

| 项目 | D1 关键词 | D2 同型 | D3 级别 | D4 角色 | D5 量化 | D6 差异 | 合计 | 建议 |
|---|---|---|---|---|---|---|---|---|
| LPL 赛事数据客户端 | 2 | 2 | 2 | 2 | 2 | 2 | 12 | ✅ 点亮·置顶 |
| 目标检测课程设计 | 1 | 1 | 1 | 2 | 2 | 0 | 7 | ✅ 点亮 |
| 交通局可视化 | 0 | 1 | 2 | 1 | 2 | 1 | 7 | ✅ 点亮（版式需要） |
| 图书管理系统 | 0 | 0 | 1 | 1 | 1 | 0 | 3 | ⏸ 收起 |

➡️ 推荐：按上表。收起的"图书管理系统"**不删除**，`visible: false` 存着，换岗位随时切回。
```

- 逐项理由必须写**命中了 JD 的哪一条**（引原文关键词），不写"感觉更相关"。
- 页数影响如实写（"约 +3 行，可能挤掉自我评价一条"）。
- 允许用户改判：改判后重排名次与总量，不辩论、不二次推销。

## 三、产出（写进改动申请单，仍走确认门）

```json
{
  "target": { "company": "", "position": "", "jdSource": "" },
  "candidates": [
    {
      "id": "projects[1]", "name": "LPL 赛事数据客户端",
      "score": 12, "dims": { "kw": 2, "fit": 2, "level": 2, "role": 2, "quant": 2, "rare": 2 },
      "hits": ["JD：Agent 编排", "JD：RAG / Text-to-SQL"],
      "recommend": "show", "reason": "唯一同时命中编排与数据链要求的项目",
      "pageImpact": "约 4 行（已在蓝本内）"
    }
  ],
  "visiblePlan": ["projects[0]", "projects[2]", "projects[3]"],
  "hiddenPlan": ["projects[1]"],
  "excludedForever": ["社会实践", "预科经历"],
  "gaps": ["JD 要求 vLLM 部署经验，候选池无命中 → 进缺口清单，不凑"]
}
```

并入申请单时：

- `projectVisibility` 原样带上（`visiblePlan` / `hiddenPlan` / `excludedForever`）；
- 每条可见性变化在 `changes[]` 里记一条：`{ "op": "visibility", "path": "projects[1]", "now": "visible:true", "proposed": "visible:false", "why": "D6 与已选项重叠", "impact": "省 3 行" }`；
- 用户裁决只是**输入**，`changes` 仍要在阶段 3.5 拿到明确批准才能实施。

## 四、硬边界

1. **未显示 ≠ 删除**：收起项保留在 JSON 里（`visible: false`）。
2. **用户明确排除项永不显示**（社会实践、预科等），不进候选池。
3. **不许凑数**：候选池不足 3 项就如实少写，或写进缺口清单；不为凑满一页拉低相关度硬塞。
4. **不许拔高**：级别、角色、数字一律照事实基线，JD 想要什么不等于你有什么。
5. **打分要能复盘**：`hits` 必须引 JD 原文，评分维度可被用户质疑并改判。
